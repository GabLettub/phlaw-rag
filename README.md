# PHLaw RAG

A retrieval-augmented chatbot that answers questions about **six landmark
Philippine Supreme Court decisions**, shows the passages each answer came
from, and politely declines anything outside those six cases.

| | |
|---|---|
| **Live demo** | _not deployed yet_ |
| **Thesis version (v1)** | [phlaw-chatbot](https://github.com/GabLitob/phlaw-chatbot) |

> **Not legal advice.** This is a portfolio prototype. Digests and answers
> are generated by a language model from the decision text and can be
> incomplete or wrong. Check them against the linked decisions.

## What it does

- **Digests**: Facts / Issues / Ruling / Doctrine for a case, written from
  its text.
- **Follow-up questions** about one case ("Do the Rules on Electronic
  Evidence apply to criminal cases?"), answered from that case only.
- **Topic search**: "Show me environmental law cases" lists the matching
  decisions with one line on why each matches.
- **Definitions**: short answers for general legal terms, labelled as
  general knowledge and not as coming from the decisions.
- **Declines** questions the six decisions do not cover.
- **Sources on every answer**: a collapsible list of the excerpts used,
  with a link to the decision.

### The six cases

| Case | G.R. No. | Topic |
|---|---|---|
| Knights of Rizal v. DMCI Homes | 213948 | Cultural heritage |
| MMDA v. Concerned Residents of Manila Bay | 171947-48 | Environment / continuing mandamus |
| Pearl & Dean v. Shoemart | 148222 | Intellectual property |
| Ang v. Court of Appeals | 182835 | Electronic evidence / RA 9262 |
| Disini v. Secretary of Justice | 203335 | Cybercrime / free speech |
| Oposa v. Factoran | 101083 | Environment / intergenerational responsibility |

Decision texts come from [lawphil.net](https://lawphil.net). Separate,
concurring and dissenting opinions are left out; only the main decision is
indexed.

## Architecture

```
 Browser ──▶ Next.js frontend (Vercel)
               chat · cases page · Notion link
                        │ POST /chat
                        ▼
              FastAPI backend (Render)
               1. route the message
                  regex (case name / G.R. no.) → LLM router → intent
               2. run the chain for that intent
                  digest | follow_up | search | general
               3. out_of_scope? verify against the index before declining
                        │                         │
                        ▼                         ▼
          Pinecone (serverless)          Groq (free tier)
          multilingual-e5-large          gpt-oss-120b  answers
          1024-dim, cosine               gpt-oss-20b   router

  Admin only:  POST /ingest and POST /digest (X-Ingest-Token)
               called by the n8n + Notion pipeline (see below)
```

## How retrieval works

**Ingestion** (`backend/app/ingest.py`)

1. Fetch the decision page, decode it (lawphil serves Windows-1252 without
   declaring it), strip navigation, and cut everything from the first
   separate or dissenting opinion onward.
2. Split into ~1,500-character chunks with 200 characters of overlap.
3. Tag each chunk with metadata: `case_id`, `title`, `gr_no`, `date`,
   `topic`, `url`, `chunk_index` and a **section** (`facts`, `issues`,
   `ruling`, `dispositive`, `notes` or `body`). The section is set from
   headings and the "WHEREFORE … SO ORDERED" paragraph, so it is
   approximate; many decisions have no headings.
4. Upsert with stable ids (`<case_id>-<n>`), deleting the case's old chunks
   first, so re-ingesting a case never duplicates it.

**Routing** (`backend/app/router.py`)

- A regex fast path catches case names, party names and G.R. numbers
  without calling an LLM. A bare name or "digest …" gives a digest; a name
  plus a question gives a follow-up on that case.
- Otherwise a small LLM classifies the message into `digest`, `follow_up`,
  `search`, `general` or `out_of_scope`, using a short card for each case.
- When a case is already open and the message refers back to it ("the
  Court", "held"), it stays a follow-up on that case.

**Answering** (`backend/app/chains.py`)

- **Follow-up:** search only that case (footnotes excluded) and always add
  its dispositive chunks, since "what did the Court decide?" questions are
  answered there but rarely rank high by similarity.
- **Digest:** three targeted queries (background, issues and reasoning,
  disposition) merged and sorted into reading order, then structured
  output into four sections. Digests are cached in memory.
- **Search:** each case is searched separately and the cases are ranked by
  their best match, so a long decision cannot crowd out the others. The
  model then names the cases that really match.
- **Declining:** a question the router calls out of scope is not declined
  right away. The model reads the best excerpt from each case and declines
  only if none match. Raw similarity scores overlap too much between
  in-scope and out-of-scope questions to use as a cut-off.
- **Grounding:** prompts say to answer only from the excerpts, say so when
  they don't contain the answer, and cite the case. Every response includes
  `sources`.

## Evaluation

`backend/eval/questions.json` holds 20 questions: digests, specific facts,
follow-ups with history, topic searches, a definition and three
out-of-scope questions. `python -m scripts.eval` runs each one through the
same function `/chat` uses and checks the intent, that the right case is
cited, that expected phrases appear, and that out-of-scope questions are
declined.

Result of the run on 2026-10-05 (`gpt-oss-120b` answers, `gpt-oss-20b`
router):

| Type | Passed |
|---|---|
| digest | 6/6 |
| fact | 3/6 |
| follow_up | 2/2 |
| search | 2/2 |
| general | 1/1 |
| out_of_scope | 3/3 |
| **all** | **17/20** |

Full table: [`backend/eval/results.md`](backend/eval/results.md). Full
answers: [`backend/eval/answers.json`](backend/eval/answers.json).

**Reading the three failures** (the checks are phrase matches, so a miss
is not always a wrong answer):

- `fact-oposa-doctrine`: a **real miss**. The answer discussed the
  political-question doctrine and left out intergenerational responsibility,
  although that passage was retrieved. The expected word "intergenerational"
  is also hyphenated ("inter-generational") in most of the decision.
- `fact-disini-struck-down`: the answer listed the correct provisions
  (4(c)(3), 12 and 19), but the model wrote "Section 12" with a narrow
  no-break space, which the plain-text check did not match.
- `fact-mmda-water-standard`: the answer was correct ("SB level"), but the
  check also required a recreation word the question did not ask for.

The checks cannot judge legal correctness. Read `answers.json`.

## Admin pipeline: n8n + Notion

Adding a decision does not need a code change. An admin adds a row to a
Notion database, and an n8n workflow indexes it.

> **Status.** The ingest workflow (A) is built and has been run end to end
> against the deployed API. The digest-page workflow (B) is **not built
> yet**: the `/digest` endpoint and a tested Code-node script exist, but
> there is no workflow that uses them.

### Workflow A: ingest (built)

```
Notion Case Queue
  new row (Status = Queued)
        │  n8n Notion Trigger, "Page added to database", polls every minute
        ▼
  GET  /health        wakes the sleeping Render service
  Notion update       Status = Processing
  POST /ingest        fetch the decision, chunk it, index it in Pinecone
        │
        ├─ success ─▶ Status = Indexed, Chunks = <count>, Indexed at = now
        └─ error ───▶ Status = Failed,  Error = <message>
```

- The Case Queue properties are Title, Case ID, G.R. No., Date, Topic,
  Source URL, Status, Chunks, Indexed at and Error. Case IDs must be
  lowercase (`gr-101083`); the API rejects anything else.
- `/ingest` replaces a case's chunks under stable ids, so queueing a case
  again re-indexes it instead of duplicating it.
- `/ingest` and `/digest` need an `X-Ingest-Token` header. n8n stores it as
  a Header Auth credential; it is never committed.
- There is deliberately no public "save to Notion" button: writes need that
  token and are admin-only.

Files: [`n8n/ingest.workflow.json`](n8n/ingest.workflow.json) (exported,
credentials not included), plus the setup guides
[`docs/notion-setup.md`](docs/notion-setup.md) and
[`docs/n8n-setup.md`](docs/n8n-setup.md).

### Workflow B: digest pages (not built)

The plan is for n8n to call `POST /digest` after a successful ingest and
create a page in a Notion **Case Digests** database, with one heading per
section. [`n8n/build-digest-blocks.js`](n8n/build-digest-blocks.js) is the
Code-node script that turns the `/digest` response into the Notion request
(it splits text under Notion's block-size limit). It has been tested with
sample data in Node, but not inside n8n or against Notion.

### What to know

- **n8n runs on the maintainer's machine** (`npx n8n`), not on a server. A
  queued row is picked up only while n8n is running and the workflow is
  active. It needs no public address because the trigger polls Notion.
- **The free Render tier sleeps when idle**, so the workflow wakes it with a
  `/health` call first. During setup one `/ingest` call returned
  `502 Could not fetch the URL` from Render and did not recur; the API now
  reports the reason (for example `HTTP 403` or `timeout`) so a repeat can
  be diagnosed.
- **The website's "How digests get into Notion" panel describes the full
  intended flow,** including Workflow B. Until B exists, digests are
  generated live in the chat and are not saved to Notion.

## Limitations

- **Six cases only.** Anything else is declined.
- **Free tiers.** The Render service sleeps when idle, so the first
  request can take about a minute. Groq limits tokens per minute, so
  answers took roughly 8–35 seconds in the evaluation. The API allows 10
  chat requests per minute per IP and 300 per day in total.
- **Name lookups are weak.** Dense search is poor at rare names. Party names
  are added as aliases for the cases, and a decline is verified against the
  text, but a name that appears only in a long caption can still be missed.
- **Model answers can omit or mislead** (see the Oposa failure above).
- **Digests are model-written.** Check them against the decision.
- **Footnotes** are indexed but excluded from search.
- **New cases added through `/ingest`** are searchable, but are not
  recognised by name until added to `backend/data/cases.yaml` and
  `cards.json`.

## Run it locally

Requires Python 3.13 and Node 20+, plus free [Pinecone](https://pinecone.io)
and [Groq](https://console.groq.com) API keys.

**Backend**

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # then fill in the keys
python -m scripts.ingest_all --fetch   # download, chunk and index the 6 cases
uvicorn app.main:app --reload          # http://localhost:8000/docs
```

`ingest_all` also takes `--dry-run` (chunk only, no Pinecone) and no flag
(re-index the saved texts in `data/raw/`).

**Frontend**

```bash
cd frontend
npm install
cp .env.example .env.local      # set NEXT_PUBLIC_API_URL
npm run dev                     # http://localhost:3000
```

**Evaluation**

```bash
cd backend
python -m scripts.eval          # writes eval/results.md and eval/answers.json
```

| Variable | Where | Purpose |
|---|---|---|
| `PINECONE_API_KEY`, `PINECONE_INDEX` | backend | vector store |
| `GROQ_API_KEY` | backend | LLM access |
| `LLM_MODEL`, `ROUTER_MODEL` | backend | model names (change here if Groq retires one) |
| `LLM_REASONING_EFFORT`, `ROUTER_REASONING_EFFORT` | backend | reasoning effort per model |

| `DAILY_REQUEST_CAP` | backend | total `/chat` requests per day |
| `NEXT_PUBLIC_API_URL` | frontend | where the API runs |
| `NEXT_PUBLIC_NOTION_URL` | frontend | link to the Notion workspace (optional) |

### API

| Endpoint | Auth | Purpose |
|---|---|---|
| `POST /chat` | public, rate-limited | `{message, history[], active_case_id?}` → `{answer, intent, case_id, sources[]}` |
| `GET /cases` | public | the six cases with their summaries |
| `GET /health` | public | `{ok, vectors}` |
| `POST /ingest` | `X-Ingest-Token` | fetch, chunk and index one decision |
| `POST /digest` | `X-Ingest-Token` | structured digest JSON for one case |
